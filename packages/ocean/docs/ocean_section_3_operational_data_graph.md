# 3. Operational Data Graph
 
## Purpose
 
The **Operational Data Graph** represents the live operational state of care delivery by making relationships between operational entities queryable.
 
- The **event backbone** records *everything that happened*.
- The **operational graph** answers *what is the current state and how are things connected?*
This enables:
 
- real-time operations
- workflow automation
- AI context retrieval (grounding)
- root cause analysis
- operational analytics
- auditability for clinical workflows
In OCEAN, the Operational Data Graph is the **context engine**.
 
## Why a Graph Model
 
Care operations are relationship-driven. Common questions require traversing connected entities:
 
- Which alerts belong to this patient?
- Which tasks were generated by this alert?
- Which care team member completed the task?
- Which interactions resolved the alert?
- Which outcomes reduced future alerts?
Instead of treating these as isolated tables, the operational graph connects them into a continuous lifecycle.
 
## Core Graph Nodes and Relationships
 
Nodes correspond to the Operational Object Model (Section 2): Patient, Clinic, CareTeamMember, Signal, Alert, Task, Interaction, Outcome.
 
Common edges:
 
- Patient → has_signal → Signal
- Signal → triggered → Alert
- Alert → generated → Task
- Task → assigned_to → CareTeamMember
- Task → resolved_by → Interaction
- Interaction → produced → Outcome
- Outcome → affects → Patient
## Example Operational Graph
 
Example workflow: patient misses a glucose reading.
 
```text
Patient
  └── has_signal
        └── Signal (missing_glucose_reading)
              └── triggered
                    └── Alert (glucose_missing)
                          └── generated
                                └── Task (call_patient)
                                      └── resolved_by
                                            └── Interaction (phone_call)
                                                  └── produced
                                                        └── Outcome (patient_educated)
```
 
## Materialization: Events → Graph
 
The operational graph is materialized from events.
 
Events flow through the backbone; projection consumers update graph nodes/edges.
 
Example event flow:
 
```text
alert.created
→ create Alert node
 
task.created
→ create Task node
→ create Alert → Task edge
 
call.completed
→ create Interaction node
→ create Task → Interaction edge
```
 
The graph becomes a near-real-time projection of operational events.
 
## Storage Architecture (Pragmatic)
 
For a small team, the simplest workable split is:
 
- Event backbone: Kafka-compatible broker (e.g., Redpanda)
- Operational persistence: Postgres (event store + graph tables)
- Graph API: GraphQL (Hasura or a thin service)
- Analytics: Snowflake + dbt
Operational queries live in Postgres; analytical queries live in Snowflake.
 
## Query Patterns
 
### Operational query: what requires action?
 
Which alerts currently require a nurse call?
 
Traversal:
 
```text
Alert → Task → CareTeamMember
```
 
Filter:
 
```text
task.status = "open"
task.type = "call_patient"
```
 
### Patient context query: what happened recently?
 
What happened to this patient in the last 48 hours?
 
Traversal:
 
```text
Patient
→ Signals
→ Alerts
→ Tasks
→ Interactions
→ Outcomes
```
 
### Root cause query: where is noise coming from?
 
Which alerts are most frequently dismissed as false positives?
 
Traversal:
 
```text
Alert → Outcome
```
 
Filter:
 
```text
outcome.type = "false_positive"
```
 
## AI Context Retrieval (Grounding)
 
The operational graph improves AI safety and relevance by retrieving structured context instead of arbitrary text.
 
Typical retrieval bundle:
 
- latest signals
- recent alerts
- open tasks
- recent interactions
- known outcomes
This structured context is then used to generate summaries, drafts, and workflow suggestions.
 
## HIPAA & Auditability
 
Because graph nodes and edges originate from events, OCEAN maintains traceability:
 
```text
signal → alert → task → interaction → outcome
```
 
This is critical for HIPAA audit trails and clinical governance.
 
## Warehouse Synchronization
 
Operational graph data should be streamed into the analytics warehouse for cohort analysis and longitudinal reporting.
 
```text
Event Backbone → Postgres Graph → Export/ELT → Snowflake → dbt models
```
 
## Operational Benefits
 
The Operational Data Graph provides unified patient context, enables workflow automation, grounds AI, and supports outcome-based learning.
