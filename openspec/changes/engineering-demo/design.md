## Goals / Non-Goals

**Goals:** one repeatable engineering story with authentic API receipts, connector mappings, batch recovery and Twenty operations; a real-data rehearsal and a shareable synthetic counterpart using the same code.

**Non-Goals:** full POCAR/PAP migration, source-system writes, production cutover, patient communications, billing submission, a new generic dashboard framework, or a replacement genesis loader.

## Decisions

Decided 2026-09-10; these choices gate implementation of this change.

1. **POCAR first, PAP second, one verified event family each.** POCAR gives operational depth; PAP demonstrates a second producer and shared identity. Starting with only a convenient export would miss those integration seams. Discovery records MCP tool schemas/versions, source ownership, read permissions, record grain, stable identifiers, change/version markers, retention, deletion semantics and source-to-catalog mapping. Inspect metadata through MCP; inspect real rows only through approved read-only execution inside the data boundary. Reuse archaeology for Mongo extraction. MCP is not assumed to be a bulk transport. If discovery cannot establish a bounded family and stable extraction contract, replan before adapter dispatch.
2. **Reuse existing contracts.** Each adapter maps into the shared connector kit and registered writer identity. Coordinate with pocar-relay; this change owns its bounded demo slice, not a second relay. Genesis seed-run owns the shared batch harness and adjudication-rules owns dbt reconstruction. Before dispatch, record the exact owning task/PR for shared work; use it here and omit duplicate implementation. If those plans have no tasks yet, this change supplies the bounded reusable slice and their later plans consume it. Two active implementation changes maximum.
3. **Explicit API surface.** Use existing authorized command submission, state retrieval and event-history routes after verifying their actual schemas in task 1.1; publish executable request examples with redacted credentials. Do not invent endpoint names in the plan. For each source, capture command, source/version correlation, idempotency key, accepted event ID, subsequent state and ordered history. A retry adds zero events; a different payload with the same key must surface a conflict, never a false success. A correction uses a catalog-supported appended event, not an UPDATE. If a required read surface is missing, record a targeted API delta before adding it.
4. **Data model.** Versioned MappingManifest contains source, source contract version, entity grain, external identity mapping, event family, state transitions, evidence requirements and Twenty mapping. BatchManifest contains immutable snapshot reference/digest, cutoff T, mapping/rule versions, cohort selector, run ID and target manifest digest. RowReceipt tracks source/version, deterministic key, status, event ID or quarantine reason and durable checkpoint. Sensitive references and payloads stay inside the approved boundary; public receipts carry only synthetic IDs or aggregate counts.
5. **Current seed and historical backfill are separate phases.** Current seed declares supported state as of T. Historical rows require evidence and preserve effective_at versus recorded_at plus reconstruction provenance; missing history is a reported gap, never invented transitions. Versioned dbt rules resolve multi-source disagreements before submission. Identity ambiguity and unsupported states quarantine. Replaying a frozen batch preserves semantic commands and keys; changed mappings require an explicit new version and reconciliation. Commit checkpoints only after durable API acknowledgement; restart reconciles uncertain responses using the same keys. A historical event that would corrupt current state is quarantined pending existing ledger temporal rules, not force-written.
6. **Twenty is a projection of the verified domain.** Mapping table per family: source field/event → catalog state/event → API read → Twenty object/relationship/state field/event view. Link person/external identity to the family record and its event provenance. Show current state prominently and key events chronologically with effective/recorded times. Preserve existing board command validation for editable transitions. Do not make Twenty an independent state authority. Test replay, duplicate delivery and late/out-of-order events against the API-derived result. Do not claim unverified enrollment or referral fields are ratified mappings.
7. **Two presentation scales.** Detail: source → API create → ledger history → appended change → API read → Twenty. Operations: cohort counts, accepted/retried/quarantined/failed rows, backlog age, processing rate, projection lag, reconciliation mismatches and recovery status, with drill-through using correlation IDs. A presenter can pause each stage, rerun it, inspect a receipt and resume. Reuse Demo5 transports/assertions and existing ops surfaces; use a small report/view for missing presentation needs. No staged green badges: timeouts and failures produce failed receipts and nonzero exit. Fault injection uses synthetic inputs only.
8. **Demo reset is environment lifecycle, not a ledger API.** A provisioned disposable target manifest allowlists database, Twenty workspace, warehouse namespace, queues/DLQs, cursor/checkpoint and identity resources, including ownership IDs. The existing Demo5 fixed warehouse target must be parameterized before reuse. Reset requires demo mode, exact target ownership verification and a preview of affected resources; refuse unknown/shared/production targets before mutation. Stop producers, fence the run generation, drain or discard run-owned pending delivery, clear only run-owned data, and verify zero ledger/current-state/outbox/identity/idempotency/checkpoint/projection/queue data. Retain a redacted reset receipt outside the reset boundary. Verify delayed old-generation delivery cannot rehydrate. Reload uses a new run generation and compares normalized semantic state, not newly generated event IDs. Projection rebuild is a different operation: preserve ledger events and reconstruct only projection-owned data.

## Risks / Trade-offs

- Source evidence is unknown → discovery is a hard entry gate; a schema-only fixture is not evidence of real-data success.
- Real PHI can leak into demonstrations → dev/staging, CI, committed examples and recordings use synthetic data; real rehearsal remains inside the approved production data boundary with aggregate receipts only.
- Batch and online streams can overlap → pin cutoff and source version boundary; verify overlap dedup and report gaps before enabling ongoing extraction. No unsupported CDC promise.
- Backfill can alter current state incorrectly → exercise temporal folding with evidenced history and quarantine unsupported sequences.
- Shared projections can survive a database reset → full resource manifest and zero checks across the graph are mandatory.
- Discovery exceeds a two-hour slice → checkpoint evidence and replan the affected slice; do not silently expand scope.

## Migration Plan

Then implement bounded adapters, reusable batch seams, Twenty model and demo lifecycle tests. Run the synthetic suite from a clean environment. Stop/fence producers on failure, preserve restricted diagnostics, and discard only verified disposable resources. Keep existing demo commands operational throughout.

## Acceptance evidence

The Engineering run must show both sources, actual API create/read, preserved original event content, retry/crash recovery, Twenty agreement, batch historical provenance, projection rebuild, reset-to-zero and reload. Record dataset/mapping versions, code revision, stage outcomes, observed counts/timings and unresolved bugs. Bugs get a reproducing test and owner before rerun; all required stages must pass for acceptance. Synthetic success and real-data success are separate receipt fields.
